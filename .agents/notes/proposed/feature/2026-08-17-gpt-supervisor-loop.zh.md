# Agent Note: GPT 监督闭环

Status: proposed

## Problem

DeepSeek Harness 已经能够委派子代理、运行由模型编写的工作流、暂停等待用户审批，并组合不同模型提供方，但目前没有一个一等的“监督者”能力：它不能在另一个代理完成工作后，根据明确策略自动判断结果是否合格，并决定接受、要求返工、补充信息或把敏感决定升级给人工审批。缺少这一层时，想搭建多岗位 AI 公司的用户仍然需要在执行者和审核者之间手工传话，既破坏自动闭环，也很难审计审批规则。

目标部署需要监督者能够独立使用 OpenAI 模型，而执行者可以继续使用 DeepSeek。监督者必须能够拒绝质量不足的结果，并自动把明确的返工意见交回执行者，不要求人工复制消息。同时，监督者不能自行批准付款、退款、具有约束力的价格变更、重要数据删除或对外重大承诺等高影响业务动作。

## Proposal

新增监督能力时，以插件形式挂在现有 agent loop 旁边，而不是修改 `packages/core/agent-loop`。第一版负责使用独立配置的 LLM 路由审核执行者已经完成的工作，生成类型化决策，再通过现有 agent、session、workflow 和 interaction 扩展点把决策送回系统。

一次审核有四种结果：

- `accept`：执行结果满足当前目标和验收标准，可以继续。
- `revise`：结果不完整或不正确；监督者返回可执行的修改要求，并让执行者进入下一次步骤。
- `clarify`：缺少必要信息且不能负责任地推断；监督者提出具体问题或查询要求，而不是猜测。
- `escalate`：下一步动作命中人工审批规则，必须暂停，等待审批服务给出结果。

监督循环必须受配置限制。它有最大审核轮数，每次决策都写入可持久化、可追溯的会话状态；监督者输出格式错误或返工次数耗尽时必须“失败关闭”，绝不能把异常当作默认通过。

### Package topology

第一版预计使用一个单一职责包，放在新的或现有的编排类目录下，暂定 `packages/workflow/supervisor`，包名 `@deepseek-ai/dsh-supervisor`。它只负责监督策略和审核编排；模型传输继续使用现有 `ctx.llm` seam，人工审批继续使用现有 interaction 能力。监督包内部不实现 OpenAI 专用 API 客户端。

该包依赖现有 agent/session/LLM 接口，并在需要时依赖 interaction approval。它不分叉、不修改模型适配器。OpenAI 路由由现有通用 `llm-pi-ai` 适配器提供，因此监督者只需要通过配置选择 provider/model，而执行者可以选择另一条路由。

### Review trigger

第一版在“执行者完成一个 turn”或显式 workflow 审核调用时触发，而不是每一个模型 step 都审核。逐 step 审核会产生不必要的模型费用和延迟，也可能干扰正常工具调用循环。插件只挂在已记录的 agent/workflow 扩展点上，并且只有 `revise` 决策才要求执行者继续下一轮。

插件必须保持 Harness 的核心不变量：模型可见的信息必须能够从持久 session state 重建。因此，监督者注入给执行者的反馈必须带明确 plugin source，并在影响下一次模型请求前进入日志。

### Supervisor request

每次监督请求只包含判断当前目标所需的证据：

- 当前目标或任务描述；
- 执行者最近一次完成的回答以及相关已记录工具结果；
- 配置的验收标准和升级规则；
- 当前审核轮次和剩余次数。

监督 prompt 强制输出符合决策联合类型的结构化结果。结构之外的自由文本不作为有效决策。实现必须在 LLM 边界验证模型输出后才能执行后续动作。

### Human approval policy

人工审批和质量审核是两个独立决策。监督者可以识别某个动作属于敏感动作，但它自己不能批准。`escalate` 必须通过现有 interaction 能力创建审批请求，并暂停后续执行，直到审批结果返回。

第一版部署策略至少把以下“真正对外执行”的动作设为需要审批：付款或转账、退款或补偿、超过配置范围的价格变更、合同或法律承诺、破坏性数据操作、凭证或权限变更，以及对客户产生重大财务或交期影响的承诺。部署配置可以增加更严格的类别。

### Automatic clarification

`clarify` 不等于立刻问老板。编排层首先判断缺失信息是否能从已经挂载的工具或连接数据源中获得。如果工具查询可以解决，执行者会收到针对性的查询指令；只有真正属于用户本人、或者系统无法获取的信息，才转成用户问题。

### Loop limits and failure behavior

审核循环提供可配置的 `maxReviewCycles`，默认值保持保守。达到上限后必须失败关闭，并显示需要人工处理的状态，而不是无限循环。监督模型的 provider 错误只通过现有 LLM retry policy 重试；监督编排本身不隐藏 provider 失败。

监督输出如果无法通过 schema 校验，属于错误，不属于 `accept`。如果某个 `escalate` 决策必须使用审批服务，但审批服务没有挂载，则必须在加载阶段或最早可判断的位置明确报错，不能静默降级为通过或返工。

### Initial deployment sequence

实现按以下顺序推进，确保每一步都容易验证：

1. 新增类型化 supervisor decision 和 policy 包，并为决策校验、循环次数、失败关闭行为添加单元测试；
2. 使用可配置 supervisor provider/model 接入现有 LLM 路由；
3. 为 `revise` 增加执行者反馈和持久日志；
4. 为 `escalate` 接入人工审批；
5. 增加可运行的 headless 示例和无密钥 snapshot，覆盖完整审核闭环；
6. 文档化一个 DeepSeek 执行、OpenAI 监督的部署 profile。

第一版不允许监督系统自动修改自己的代码或监督策略。等审核、审计和回滚机制证明可靠以后，再考虑 self-modification。

## Alternatives considered

**直接修改 `agent-loop`。** 不采用，因为 Harness 明确要求新行为优先使用已有插件扩展点。分叉主循环会增加未来同步 DeepSeek Harness 上游版本的冲突，也会让监督功能和所有代理运行强绑定。

**执行和审核都只使用 DeepSeek。** 不作为唯一架构，因为当前部署明确需要独立 GPT 审核，而且不同模型之间的交叉检查有价值。监督能力保持 provider-neutral，以后可以在配置里改成 DeepSeek、OpenAI 或其他路由，不需要再次分叉代码。

**把监督者做成仓库外部独立脚本。** 不作为主路径，因为这会重复 session、工具、审批和 workflow 的基础设施，并把“人工传话”问题换到另一个边界。外部自动化仍然可以通过 ACP 或 SDK 驱动 Harness，但审核语义应当属于插件组合本身。

**监督者判断安全后直接执行敏感动作。** 不采用，因为质量判断和人的授权权力不是同一件事。即使监督者强烈建议继续，敏感动作仍然必须经过现有 approval 能力。

**V1 就启用 self-modification。** 不采用，因为在审核和审批路径还没有经过验证前，让自主监督者能够改写自己的执行规则会增加不必要的控制风险，也让回滚更困难。

## Acceptance criteria

- 一个 profile 可以分别配置执行模型路由和监督模型路由，不需要修改任何模型适配器。
- 执行者完成结果后可以被审核，并得到 `accept`、`revise`、`clarify`、`escalate` 四种经过校验的决策之一。
- `revise` 能把明确、已记录的修改意见自动交回执行者，并在不需要人工传话的情况下进入下一次有限审核循环。
- `clarify` 能把可查询的缺失信息交给工具查询，把系统无法获得的信息交给用户提问。
- `escalate` 在人工审批完成前不能继续受保护动作。
- 监督输出无效、缺少必要审批基础设施、审核次数耗尽时，都不能隐式变成通过。
- 每一条会影响模型的监督指令都可以从持久 session state 重建。
- 提供一个可运行的 headless 示例，展示 DeepSeek 执行、OpenAI 监督，并用无密钥 snapshot 覆盖组装后的控制流。
- 不能仅为了实现监督功能而修改核心 agent-loop。

## Risks

增加模型审核会增加延迟和 token 成本，因此监督范围必须明确，不能默认审核每一个低价值步骤。

即使使用结构化输出，监督模型仍可能判断错误。人工审批规则可以降低高影响动作的风险，但普通 `accept` 结果仍然具有概率性，部署方需要给不同岗位配置具体验收标准。

升级策略太宽会让系统重新变成人工流程，太窄则会增加业务风险。第一版优先使用明确、可审计的策略字段和失败关闭，而不是隐藏式启发规则。

独立模型提供方意味着额外的凭证、额度和可用性故障。模型传输和重试继续由现有 LLM seam 负责，监督包不创建第二套网络栈。
